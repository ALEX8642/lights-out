# 0008 — Replay matching: equivalent commands and closed-world hosts

Date: 2026-11-17. Status: accepted. Amends 0003.

## Context

A scenario answers commands from recordings keyed by the exact argument list (record 0003).
After the policy stopped blocking harmless reads (record 0007), the second real-model drill
refused nothing, but 35 of its 43 commands got "no output recorded". The model asked
`dig @10.20.0.3 nas.lan +short +noall +answer`, the same question as the recorded
`dig nas.lan @10.20.0.3`, and learnt nothing. It also asked about files and services that do not
exist on that host (an Unbound configuration on the primary resolver), which a real host answers
with "No such file or directory": an answer that is itself evidence.

Replaying both real drills' allowed commands against the v0.2 scenario: 23 of 76 answered.

## Decision

A recording answers a command in one of three ways, tried in order, and the transcript records
which (`matched`: `exact`, `equivalent` or `derived`):

1. **Exact.** The argument lists are identical.
2. **Equivalent.** Both reduce to the same question under fixed per-program rules
   (`lights_out.targets.RULES`): arguments in any order; presentation-only options dropped
   (`dig +short +noall +answer +stats`, `journalctl --no-pager -n N -o FORMAT`, `systemctl
   --no-pager -l`, every `ls` option, `grep -n`); default values dropped (`dig ... A`,
   `-t A`); synonyms unified (`ip a` = `ip addr show`, `--unit` = `-u`); `.service` dropped from
   unit names; combined short flags compared as letter sets. For socket listings (`ss`,
   `netstat`, `sockstat`) a recording that shows more answers a narrower question. `cat` of
   several files joins each file's recording. A different server, record type or reverse lookup
   is a different question.
3. **Derived**, only on hosts the scenario marks `closed_world = true`. The recordings are taken
   as the host's whole state:
   - a path that no `cat` recording reads and that is not a directory above one does not
     exist, and `cat`, `head`, `tail`, `wc`, `grep` and `ls` say so as the real tools do;
   - `grep`, `head`, `tail` and `wc` of a recorded file are computed from its recorded content;
   - `ls` of a directory lists the recorded files below it;
   - with a recorded service listing (`systemctl list-units`, `service -e`), a service missing
     from it does not exist: `systemctl status` says the unit could not be found, `journalctl -u`
     says there are no entries, `service NAME status` says it does not exist.

The first matching recording in file order wins. Nothing is generated by a model.

## Alternatives considered

- **Record every plausible variant by hand.** Scales badly and still misses the model's next
  phrasing. Rules capture the variants once, for every scenario.
- **A model simulating the hosts.** Answers anything, but the same drill would no longer give the
  same transcript, and the simulator could leak or invent evidence. Rejected for scoring;
  possibly useful later for writing recordings, reviewed by a person.
- **A real sandbox per scenario.** Most faithful, and still possible later for some incidents.
  Recordings plus deterministic rules are enough to measure what the model asks and concludes.

## Consequences

- Replaying both real drills' allowed commands: 67 of 76 answered (33 exact, 10 equivalent,
  24 derived), 9 still unrecorded.
- **Equivalent answers can differ in form from what a real host prints**: `dig +short` gets the
  full answer, `ls -l` gets names only. The content is right; the formatting is not. The
  transcript's `matched` field makes every such answer visible.
- **A closed world is a claim by the scenario author** that nothing else of interest exists on the
  host. A careless author can turn a real gap into a false "No such file". Mark a host closed only
  after listing its services and the files its fault involves.
- The rules are part of the instrument. Adding or changing a rule changes which commands are
  answered in every scenario; rules change only with tests and a changelog entry.
